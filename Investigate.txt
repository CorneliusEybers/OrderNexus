Database Design:
----------------
- I decided to use Entity Framework as my Object Related model
- I decided to use code-first with take-on data and migrations
  This help you to spin up without an initial DB
- All primary keys of all tables will be named Id
- All table names to be in singular
- All foreign keys prefixed with full/exact  referenced table name plus "Id"
  Foreignkeys names TableName + Id
- Core tables identified from the spec
  ~ Order
  ~ OrderItem
  ~ OrderStatus
  ~ Item
  ~ Currency
  ~ SalesRep
- Regarding Items.
  ~ It is not in the scope to CRUD Items
  ~ I will populate the Item table with 5 items
  ~ This to ensure the Angular UI is not cumbersome
    for the user to type in every item name.
  ~ On item selection the Item-Unit-Price at that point in time
    will be used as the OrderItem-Unit-Price to keep the
    price as at order creation in case the price fluctuates
    in the back ground after the order is captured.

Application Creation:
---------------------
- I chose the name for the application as OrderNexus.
  It is a short easy name to for people to use and remember.
  Nexus comes from Latin and means a connection, binding, link, or joining together...
  a central connection point between several things.
  OrderNexus communicates the idea of 
  bringing customers, sales representatives, products, and orders 
  together into one coordinated system.
  OrderNexus has a natural phonetic resemblance to LexisNexis, without copying its exact name.

Application Architecture:
-------------------------
OrderNexus.API - Exposes the REST API endpoints and handles incoming HTTP requests/responses.
               - References: OrderNexus.Application, OrderNexus.Domain, OrderNexus.Infrastructure
OrderNexus.Application - Contains application use cases, business workflows, and service orchestration.
                       - References: OrderNexus.Domain
OrderNexus.Domain - Contains the core business entities, enums, rules, and domain behaviour.
                  - References: None
OrderNexus.Infrastructure - Contains external integrations, in-memory persistence, and technical implementations.
                          - References: OrderNexus.Application, OrderNexus.Domain
OrderNexus.Tests - Contains automated tests for critical business rules and application behaviour.
                 - References: OrderNexus.Application, OrderNexus.Domain

Runnable vertical slice:
------------------------
- For this assessment I am going to focus on Order Creation with OrderItem and Item selection
  I will do CRUD for Order and OrderItem in as-much-as creating and order with line items.
  No CRUD for Items(Product) will have TakeOnData for these items to be selectable
  No CRUD for Currency will have TakeOnData for these items to be selectable
  No CRUD for Order Status will have TakeOnData for these items to be selectable
  No CRUD for Sales Reps will have TakeOnData for these items to be selectable
  No CRUD for Customers will have TakeOnData for these items to be selectable
- Creating, editing or deleting submitted orders must respect the business rules.
- OrderItems will be managed through the Order aggregate, 
  not through an independent controller permitting unrestricted changes.
- Data will be stored in SQLite via EF Core.
- Fluent API configuration discovery
- We will implement automatic UTC timestamp assignment
- Item that can be placed into an Order as a n OrderItem
  ~ Every product requires a unique SKU.
  ~ A catalogue price cannot be negative.
  ~ UnitPrice is stored as a SQLite INTEGER.
  ~ A product referenced by an order cannot be 
    deleted through cascading relationships.
- Order Duplicate prevention
  ~ The unique index on CustomerId + ExternalReference ensures that 
    SQLite cannot store two orders with the same reference for the same customer.
  ~ Application service will first look for an existing submission and 
    decide whether to return the existing order or respond with 409 Conflict.
  ~ The database unique index is our final protection against concurrent requests. 
    Catch unique-constraint failures appropriately
    NOT allowing them to surface as HTTP 500 errors.
  ~ Normalize references consistently before saving, 
    so variations in surrounding whitespace or letter 
    casing don't accidentally evade our chosen duplicate policy.
  ~ CreatedBy and UpdatedBy remain nullable for now. 
    When we eventually introduce authentication, 
    we could populate them from the authenticated user. 
    Authentication is outside this assessment's scope.
